# Shared Xero Hub

All outbound Xero requests and token refreshes now belong to [Xero Hub](https://github.com/Sensible-Solar/xero-hub). Configure XERO_HUB_URL and XERO_HUB_TOKEN in the app and existing scheduled-job environment. On app-01 the URL is http://127.0.0.1:8010. Keep the existing Xero webhook signing key to verify and forward signed deliveries; it is not an API credential.

## Live admin contact lookup

**Companies → Search Xero** uses the Hub's authenticated live contact lookup, rather than its stored Contacts projection. A search sends one Xero `GET /Contacts` with `searchTerm`, `page=1` and `pageSize=50`. Paging includes `ContactPersons`; `summaryOnly` is omitted because it excludes those people. Results show the Xero Contact ID so an administrator can distinguish companies with similar names. If more than 50 contacts match, the administrator narrows the search. Creating a company sends one live `GET /Contacts/{ContactID}` to confirm the company and every selected primary/additional email before any local company or buyer is saved. Choosing a search result, ticking people, opening the page, viewing existing companies and sending setup emails make no Xero calls. The normal Hub contact reconciliation schedule is unchanged. Its stored evidence must be newer than a newly created company or buyer before it can change that name or revoke that access.

API budget review: each explicit search costs at most one Xero call; each creation attempt costs at most one more; cold state has the same cost. The Hub caps these **combined** admin lookups at 100 per tenant per UTC day (02:00 South African reset), spaces them by at least three seconds with a short wait when needed, and applies its existing 150-call daily reserve. Its shared connector logs source and returned allowance headers, observes `429`/`Retry-After`, and uses a 30-second outbound timeout. There are no automatic retries, scheduled calls, backfills or provider calls from field edits or page loads. The normal Hub baseline is approximately 266 calls per tenant per day before webhooks and pagination; Xero's published tenant limits are 60 per minute and 1,000 daily on Starter or 5,000 on higher tiers. An exhausted lookup cap, protected reserve, Xero pause or unavailable Hub stops the action and leaves the selected Store company unchanged. The live lookup requires an explicit `contacts:lookup` capability grant for the Thanda Store service identity; deploy the Hub endpoint and grant that capability before enabling the Store UI. The endpoint and parameters were checked against the official [Xero Contacts OpenAPI operation](https://github.com/XeroAPI/Xero-OpenAPI/blob/master/xero_accounting.yaml) and [Contacts guidance](https://developer.xero.com/documentation/api/accounting/contacts); the limits follow [Xero's rate-limit guidance](https://developer.xero.com/documentation/best-practices/api-call-efficiencies/rate-limits/).

## Create missing Victron products

The review list separates **Needs action**, **Awaiting Xero sync**, and **Reviewed / archived** with mutually exclusive counts. **Create in Xero** automatically loads a local saved-price preview; only **Create product** submits the confirmed command. **Other actions** provides the saved-Xero-list check, Do not stock, Mark as discontinued and applicable undo/restore actions. Supplier evidence is required only for discontinuation; optional notes and accounting details are collapsed. Explicit Replaces / Replaced by labels come from directed succession records, with retail aliases treated as the same stock article. This UX change adds zero supplier/Xero requests; existing command limits and server-side validation are unchanged.

Data health → Review missing Xero items → Create in Xero → review prices → Create product creates a tracked **definition only**. It never sends stock quantities, opening balances, receipts or adjustments. Cost is the normal E-Order ZAR ex-VAT account price; selling price is the E-Order ZAR list price, or normal cost / 0.525 when list is missing, rounded to cents, not the quantity-break price. Preview and confirmation both validate the saved complete catalogue evidence (maximum age 24 hours); changes require a fresh preview. Accounts match existing Thanda Victron items: inventory 631, COGS 311 / INPUT3, sales 201 / OUTPUT3. Hub independently validates the chart of accounts and the dedicated `victron:write` capability on the separate catalogue service identity. Ordinary customer-facing identities must not receive that capability.

The command uses create-only PUT /Items, never update-or-create. Existing SKUs are rejected. Hub serializes item commands and durably records approved outcomes; any uncertain command blocks its affected SKUs. An uncertain result requires maintainer reconciliation in Xero; never bypass it by manually creating a duplicate. A successful create is shown as awaiting the normal Xero stock import; Store does not manufacture a zero stock observation from the action.

API budget review: previews and page loads use local data only (zero provider calls). Each confirmation costs at most one filtered Xero GET /Items and one PUT /Items, with no automatic retries. The Hub limits these to 100 requests per UTC day (reset at 02:00 South African time), paces actions at 15 seconds and preserves its 150-call daily reserve and Retry-After. Staff-facing pause messages use plain language: the remaining seconds before trying again, or the next South African reset date/time. They distinguish the short wait from the daily limit and confirm that the paused action changed no products. No new polling is added. Both calls use source-attributed Hub request/allowance logs. The official Xero OpenAPI defines the Items GET `where` filter and create-only PUT; the official OAuth scopes reference includes Items in `accounting.invoices` as well as `accounting.settings`.

The normal complete E-Order catalogue scan also records purchasing retirement. A known predecessor with confirmed zero supplier stock or confirmed catalogue absence is archived from purchasing; `Available until stock 0` items are archived on confirmed zero or absence. Failed, malformed, empty or incomplete scans do not establish absence. No extra supplier calls are made. Relationships remain in `victron_sku_successions`; catalogue, stock and sales history are retained. Reviewed / archived exposes the reason and a reversible purchasing override. Retirement is local, not Xero archival; obsolete SKUs remain ineligible for automatic creation even when restored for review. A later complete observation showing renewed availability clears the automatic retirement reason.

The Thanda service identity permits only thanda-solar. The portal still checks signed-in users and their linked Xero customer before sending actor/contact context for quote or PDF commands. Normal catalogue/admin pages read application projections or stored Hub evidence. Explicit quote/PDF operations may cause an audited Hub request. OAuth management redirects authorised administrators to Sensible Cloud.

Stock/planning remains on the 30-minute timer, webhooks on five-minute workers, and history/contact reconciliation on existing daily timers. These jobs consume no Xero allowance; the Hub owns synchronisation, freshness and rate-limit handling. Full stored collections are validated before replacing snapshots. Customer document caching and SKU-family rules are unchanged.

Remove XERO_CLIENT_ID, XERO_CLIENT_SECRET, XERO_TOKEN_PATH and active token files after cutover. API allowance status and CODEX_ALERTS now use the Hub ledger. The shared service API and its operations document define complete source data, observed history, unknown quote outcome recovery and rollback precautions. Never restore old refresh tokens while the Hub is running.

The Data health creation action now uses the dedicated catalogue identity and reviewed `commands/victron-items` command, so its pricing agrees with the two-company catalogue review. The older Hub `commands/items` API remains available for existing consumers, but the Store no longer calls it. See [daily catalogue review](victron-catalogue-review.md) for the new capability and rollout requirements.
